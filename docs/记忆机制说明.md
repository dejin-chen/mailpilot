# MailPilot 记忆机制说明

## 1. 两类记忆

### 短期记忆

短期记忆属于某一次 LangGraph 任务：

- 当前邮件和分析结果。
- 节点执行位置。
- 工具结果。
- 草稿和审批等待状态。
- 错误、Token 和执行计数。

由 Checkpointer 按 `thread_id` 保存，服务重启后可以恢复。

### 长期记忆

长期记忆属于用户，可跨多个任务共享：

- 邮件语气与签名。
- 常用称呼。
- 重要联系人。
- 时区。
- 偏好/禁止会议时段。
- 常用会议时长。

按 `user_id` 和记忆类型隔离。

## 2. 三份存储为什么都需要

| 存储 | 作用 |
|---|---|
| `memory_profiles` | 稳定记忆身份、类型和当前版本 |
| `memory_profile_versions` | 每次变化的不可变正文、来源和时间 |
| LangGraph Store | Graph 运行时快速读取的同步副本 |

业务表是事实来源，Store 不是用户直接编辑的主数据库。

## 3. Namespace

```text
(应用版本, user_id, memory_type)
```

同一用户不同 `thread_id` 可以共享长期偏好；不同 `user_id` 即使记忆名称相同也不会共享。

`thread_id` 不能代替 `user_id`：

- thread_id 隔离一次执行。
- user_id 隔离一个人的业务数据。

## 4. 读取流程

```text
启动新邮件任务
→ 从业务记忆表读取当前版本
→ 同步到 Store 并清理已删除副本
→ load_memory 节点只读所需类型
→ 邮件风格进入草稿 Prompt
→ 日历偏好只作为约束参考
→ 真实时间仍必须查询 Calendar MCP
→ 使用过的记忆 ID/版本写入 State 和 AgentRun
```

不把全部历史对话塞进 Prompt。

## 5. 更新流程

```text
用户提供审批反馈
→ Python 检查“以后、默认、请记住”等长期信号
→ LLM 只生成结构化局部 Patch
→ Python 检查证据来自反馈原文
→ MemoryService 锁定当前档案
→ Patch 合并旧值
→ 追加不可变新版本
→ approval_request_id 唯一约束防重复恢复
→ 写 AuditLog
```

模型不能直接覆盖整份记忆，也不能直接写数据库。

## 6. 查看、修改和删除

- 用户可以通过 API/UI 查看自己的当前记忆。
- 版本历史解释“何时、因为什么来源发生变化”。
- 修改必须携带 `expected_version`，防止旧页面覆盖新数据。
- 删除业务记忆后，下一个任务同步时会清理 Store 副本。
- 其他用户访问统一返回 404。

## 7. 偶然反馈和长期偏好

“这封邮件写短一点”只影响当前草稿。

“以后给供应商的邮件都简洁一点，请记住”才可能形成长期偏好。

即使存在长期信号，也只生成局部 Patch。例如只修改 `tone`，不能顺便清空签名和称呼。

## 8. Checkpointer 与 Store 的职责边界

> Checkpointer 保存某个 thread 的执行现场，让工作流从 interrupt 后继续；Store 保存可以跨 thread 复用的长期信息。前者更像游戏存档，后者更像用户通讯录和偏好设置。MailPilot 另外使用业务记忆表提供可查看、版本化和可删除的事实来源。
